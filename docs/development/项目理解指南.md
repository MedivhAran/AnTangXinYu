## 一、这是个什么东西

**安糖心语**是一个面向 **1 型糖尿病 / 妊娠糖尿病 / 低血糖恐惧情绪**用户的中文陪伴型 AI。

它不是医生,也不替代医生。它更像一个永远在线的、有医学常识也有情绪敏感度的"朋友":你血糖偏低的时候它陪你聊几句、提醒你补糖;你刚做完一次连续血糖监测(CGM),它能解读那份评估报告,把"这 13 天里你哪一天偏低、哪一段血糖容易冲高"用人话讲给你听;你害怕又一次半夜低血糖了,它先接住你的情绪,再讨论要不要做什么。

它的对话节奏跟普通 ChatGPT 不一样,**第一轮优先接情绪,而不是上来甩 1234 条建议** —— 这是产品方向定下来的,直接写在了主 Agent 的 system prompt 里。

技术上它是个**前后端分离的 Web 应用**:

- 前端 Vue3,只剩一个对话界面(其它管理类页面已经隐藏,只能通过直接输入 URL 访问)。
- 后端 FastAPI + LangChain/LangGraph + MySQL + Redis + MinIO + Chroma 向量库。
- 用了至少 4 个 LLM 角色,每个角色干不同的事(下文展开)。

## 二、跟它聊一句话,后端到底跑了什么

新手最容易迷失的地方是"看代码看不出来一次对话的全流程"。这里完整走一遍。

假设用户在前端输入:**"我刚跑步回来,血糖 4.2,有点慌"**

### 1. 前端 → SSE 入口

前端 POST 到 `/api/v1/completion/stream`,带上 `user_input`、`dialog_id`,以及可选的 `glucose_context`(用户填的血糖数值)和 `file_url`(如果带了图片/PDF 附件)。

这是个 SSE 流式接口,后端边算边推 token。

### 2. 实例化主 Agent

`api/v1/completion.py` 拿到请求后,从数据库读出"安糖心语"这个 Agent 的配置(模型 ID、绑定的 MCP / Skill / Tool 列表、system prompt),实例化一个 `AnTangAgent`(继承自 `GeneralAgent`)。

**`AnTangAgent` 是 per-request 实例化的** —— 每次对话起一个新实例,对话结束就丢。所以可以在 `self.current_*` 字段里塞本轮的图片 URL、血糖上下文、light_analyzer 输出之类的"本轮临时状态",不用担心跨请求污染。

### 3. 三件事并行启动

`AnTangAgent.astream()` 里做了两件**并行**的事:

- **长期记忆召回** —— 调 `AnTangProfileService.recall_context()`,从 MySQL 读用户画像 + 从 Chroma 向量库做语义检索,返回"这个用户的长期特征 + 跟这句话相关的历史对话片段"。
- **轻量分析器** —— 调 `light_analyzer.analyze()`,跑一个小模型(默认 `qwen-turbo`,约 1-2 秒),它不参与对话,只输出一个 4 段备忘录:`understanding`(本轮在发生什么)、`core_worry`(用户具体怕什么)、`reply_rhythm`(建议的回复节奏)、`avoid`(本轮最该避免的坑)。

记忆召回通常 < 1 秒,分析器 1-2 秒,所以最后是 `await` 分析器这一边,记忆基本是零等待。

### 4. 拼 system prompt

`build_turn_system_prompt_v2` 把以下东西拼到一起:

```
[DEFAULT_ANTANG_SYSTEM_PROMPT 原文]
+ [light_analyzer 备忘录]    ← "用户在表达跑后低血糖恐惧,核心怕又一次半夜低血糖"
+ [当前血糖区间分类]          ← classify_glucose_zone:4.2 落在"偏低"
+ [长期记忆片段]              ← "用户有过类似经历,跑前 1 小时容易低血糖"
+ [短期对话历史摘要]          ← 如果历史超过阈值会有压缩摘要
```

这一拼,主 LLM 就拿到了一个**远比普通 ChatBot 更聚焦**的提示词。

### 5. 主 ReAct 循环

调用 LangChain 的 `create_agent`(ReAct 风格)。模型看到 system prompt + 用户消息,自主决定:

- 直接回话?
- 调工具?(查天气、查糖尿病知识库、读最近 CGM 报告、解读 CGM、查时间……)
- 调 MCP?(高德地图、必应搜索、飞书)
- 调 Skill?(子 Agent 处理专项任务)

**这里有个核心抽象 —— 主 Agent 眼里,MCP / Skill / 本地 Tool 都是 langchain `BaseTool`**。每个被包装成一个函数签名,模型按 description 决定要不要调。详细机制看下面"Sub-Agent as Tool"那节。

回复一边流给前端(SSE response_chunk),一边累积在 `response_content` 里。

### 6. 对话收尾(finalize_turn)

ReAct 跑完后,SSE 关闭之前,后端在 `finally` 块里调 `AnTangAgent.finalize_turn`,**fire-and-forget 启动两个后台任务**(不阻塞 SSE 关闭、不让用户等):

- `_store_turn_memory_safely` —— 把这轮 user / assistant 消息写进向量记忆库(mem0 + Chroma)
- `_update_profile_safely` —— 跑一次结构化 LLM(`StructuredResponseAgent`),根据"旧画像 + 本轮对话 + light_analyzer 的 understanding"重写画像 9 个字段,然后写回 `antang_profile` 表

这两个任务每个 2-5 秒,但用户已经看到回复了。

### 7. 历史落库

`HistoryService.save_chat_history` 把 assistant 消息 + 所有中间事件存进 `history` 表(后面前端展示历史用)。

### 8. 对话状态更新 + 上下文压缩

`DialogService.update_dialog_summary` 检查这次对话的累计 token 是否超阈值,超了就跑一次"对话总结"压缩短期历史。

至此一轮对话完成。

## 三、三个角色的 LLM,各干各的

很多人看代码的时候会问"为什么这个项目要起 3 个 LLM client?" —— 它们分别对应**三种成本/速度/能力档位**:

| 角色 | 默认模型 | 速度 | 用在哪 |
|---|---|---|---|
| **主对话模型** | `qwen3.6-plus` / DeepSeek 等 | 慢但聪明 | 主 ReAct 循环,生成给用户看的话 |
| **轻量分析器** | `qwen-turbo` | ~1.6 秒 | 每轮对话开始前的"情境备忘录" |
| **结构化抽取器** | 同主对话模型 + `ToolStrategy` | 慢但 schema 强约束 | 画像更新、CGM 报告字段抽取、MCP 工具名生成等需要"准确 JSON 输出"的场景 |
| **视觉模型** | `qwen3-vl-plus` | ~3-5 秒 | 用户上传图片时的图像理解(餐食 / 血糖仪截图等) |
| **Embedding** | `text-embedding-v4` | 快 | 知识库 + 向量记忆 |
| **Rerank** | `gte-rerank-v2` | 快 | 知识库检索的二次精排 |

设计取舍是:**该贵的地方贵,该快的地方快**。轻量分析器是这个项目的一个细节亮点 —— 主对话模型很贵很慢,如果让它每次都重新"理解上下文",成本和延迟都高;先用一个快模型把"用户这轮在干嘛"提炼成 4 句话注入到主对话的 prompt 里,主对话就能更聚焦地一次答到位。

实测下来,加了轻量分析器之后,主对话第一次回复就能切中情绪,**少了一轮"我先共情再问你怎么了"的尴尬展开**。

## 四、"Sub-Agent as Tool" —— 这是这个项目最值得理解的设计

整个项目把 **MCP Server / Agent Skill / 内置工具** 这三种完全不同的东西,**统一收成 langchain 的 `BaseTool`**。

看 [`core/agents/general_agent.py`](../../src/backend/AnTang/core/agents/general_agent.py) 的 `init_agent`:

```python
self.mcp_agent_as_tools = await self.setup_mcp_agent_as_tools()       # MCP → Tool
self.tools = await self.setup_tools()                                  # 普通 OpenAPI / 内置 Tool
self.skill_agent_as_tools = await self.setup_agent_skill_as_tools()    # Skill → Tool
```

最后这三类全部拼到一起塞给 `create_agent`。主 Agent 的 LLM 根本不知道哪些工具背后是 MCP 协议、哪些背后是另一个 LLM,它只看到一个工具列表 + 每个工具的 description,自己决定要不要调。

### Skill 的具体包装方式

[`general_agent.py:281-307`](../../src/backend/AnTang/core/agents/general_agent.py#L281-L307) 这段:

```python
@tool(agent_skill.as_tool_name, description=agent_skill.description)
async def call_skill_agent(query: str):
    skill_agent = SkillAgent(agent_skill, self.agent_config.user_id)
    await skill_agent.init_skill_agent()
    messages = await skill_agent.ainvoke([HumanMessage(content=query)])
    return "\n".join([message.content for message in messages])
```

每次主 Agent 调这个工具,**后端 new 一个 `SkillAgent` 实例,把那个 skill 的整个 folder JSON 加载进去**,跑一个**完整的 ReAct 循环**(它内部还有自己的 LLM 调用、自己的 system prompt = SKILL.md),最后输出一段字符串,作为工具结果返回主 Agent。

这就像主 Agent 雇了一个一次性的"专业临时工",干完活就丢。**两个 LLM 之间只通过字符串通信**,SkillAgent 看不到主对话的历史、看不到数据库、只能读自己 folder 里的 reference / scripts 文件。

这种隔离是有意的 —— 既能给 SkillAgent 设很强的输出约束(SKILL.md 是它的 system prompt),又不会污染主 Agent 的 prompt 上下文。

### MCP 也是同款机制

[`general_agent.py:309-349`](../../src/backend/AnTang/core/agents/general_agent.py#L309-L349) 包装 MCP 的逻辑跟 Skill 几乎一模一样。每个 MCP Server 包成一个 `MCPAgent`,`MCPAgent` 再包成一个 langchain tool。主 Agent 调它时,`MCPAgent` 内部跑一次 ReAct,通过 MCP 协议跟远程服务通信,把结果包成字符串回来。

## 五、长期记忆系统

这是项目里**第二容易看不懂**的地方:有两套机制,而且历史上长期处于"代码写好但没接通"的状态,最近才打开。

### 两层结构

| 层 | 存哪 | 存什么 | 用在哪 |
|---|---|---|---|
| **结构化画像** | MySQL `antang_profile` 表 | 9 个字段:常见低血糖时段、诱因、夜间倾向、饮食偏好、运动模式、情绪模式、安抚偏好、近期风险、摘要 | 每轮对话开始前注入主 prompt 的"用户长期特征"段 |
| **向量记忆** | Chroma(走 mem0) | 每轮 user/assistant 对话的语义化片段 | 每轮按用户当前问题做语义检索,捞出相关历史片段拼到 prompt |

### 写入是 fire-and-forget

[`antang_agent.py:finalize_turn`](../../src/backend/AnTang/core/agents/antang_agent.py) 用 `asyncio.create_task` 启两个后台任务:

- 一个是把对话写进向量库(包含 LLM 抽事实、合并去重、embedding,3-10 秒)
- 一个是把"旧画像 + 本轮对话"喂给结构化 LLM,生成新画像写回 MySQL(2-5 秒)

**两个任务都不阻塞主对话返回**。即使失败也只 warning,不抛异常。

### 读取是并行的

[`antang_agent.py:astream`](../../src/backend/AnTang/core/agents/antang_agent.py) 里召回任务跟 light_analyzer 是并行起的 task,通常 light_analyzer 慢一点,所以 `await recall_task` 的时候记忆已经准备好了。

### 为什么这套设计有意思

很多 AI 陪伴产品的"记忆"只是简单 RAG 一段 chat history。这里做的更细:**结构化画像反映"用户长期特征"(常见低血糖时段、安抚偏好等),向量记忆反映"具体说过什么"**。两者在 prompt 里分两段注入,主 LLM 能区分"这是用户的稳定模式" vs "这是上次提过的具体事件"。

### 历史问题

`update_profile` 这个写入路径长期被**有意关闭**(注释里写了原因:等召回 + 向量写入这条线跑稳再单开)。最近接通时发现两个小问题:
1. 函数签名要 `AnTangStateAssessment`,但 light_analyzer 实际输出是 `LightAnalyzerResult`。改成接 `assessment_reason: str` 字符串就行,内部只用了那个 reason 字段。
2. 每轮都触发一次结构化 LLM 调用,聊得密时一小时几十次。后续如果成本/速度有压力,可以加 Redis cooldown 节流(目前没加,先观察)。

## 六、Skill 系统:从"用户可建"到"后端开发者维护"

这是这个项目演化里**最大的一次方向调整**。

### 原来是怎样的

原来设计是:用户在前端有一个"Agent Skill"管理页面,可以自己创建 Skill、上传文件、编辑 SKILL.md(前端集成了 Monaco 编辑器)。后端有完整的 CRUD API。

### 为什么改

产品方向收敛了:**普通用户的入口只剩聊天**,所有 Skill / MCP / Agent 管理界面都不再暴露。理由:

- 让用户自己写 SKILL.md,事实上几乎没人会写
- 用户写的 Skill 质量参差,对医疗陪伴场景有合规风险
- 客服 / 运营调起来痛苦(用户写错了你不知道哪里错)

### 现在是什么样

Skill 完全收归后端开发者管理:

1. 开发者在 `src/backend/AnTang/skills/<skill_name>/` 建目录,放 `SKILL.md` + `reference/` + `scripts/`
2. `SKILL.md` 的 frontmatter 必须含 `name` 和 `description`
3. 后端启动时,[`_init_system_skills`](../../src/backend/AnTang/database/init_data.py) 扫描这个目录,递归把文件读成 JSON,upsert 进 `agent_skill` 表(`user_id = SystemUser '0'`)
4. [`_ensure_antang_agent`](../../src/backend/AnTang/database/init_data.py) 查询所有 SystemUser 的 skill 自动绑到"安糖心语" Agent 的 `agent_skill_ids`
5. 运行时主 Agent 在工具列表里就有这个 skill,可以按需调用

**重要**:`SkillAgent` 运行时还是从数据库的 `folder` JSON 读 skill 内容,**文件夹只在启动 seed 时被读一次**。所以改了 SKILL.md 必须重启后端(并且开 `refresh_system_skills_on_startup: true` 才会覆盖已存在的同名 skill)。

### 怎么解释"为什么有 skills/ 这个目录"

它不是运行时被读的资源目录,它是**"系统 Skill 的源代码"**,启动时同步进数据库。改它就像改源码,需要重启。

### MCP 完全同款

MCP Server 同样改成"后端开发者维护"。`config/mcp_server.json` 列出所有系统 MCP,凭证(比如飞书的 app_id/app_secret)统一放 `docker_config.yaml` 的 `mcp_credentials` 段。前端不再有"用户创建 MCP"的界面,后端 `mcp_server.py` 等路由文件保留但 `router.py` 不挂载它们。

## 七、CGM 报告处理:整套链路

这是项目最近一次大功能扩展。讲清楚它怎么跑,因为它把前面所有机制都用上了。

### 业务场景

合作方提供了硅基仿生 CGM 设备的**患者评估报告**(动态葡萄糖监测,2 周左右的血糖时序数据 + 多种统计指标,PDF 形式)。用户用这种设备做完监测就会拿到一份这样的报告。

我们要做的是:让 AI 能"全面详细地解析这些 CGM 用户报告,并为用户提供长期支持"。

### 两条上传路径,一个共用 service

```
路径 A: 专门上传板块             路径 B: 对话附件
前端 /cgm/upload 板块           主对话里上传 PDF 附件
    │                               │
    ▼                               ▼
POST /api/v1/cgm/import        主 Agent 看到 file_url
    │                               │
    │           调内置 Tool `import_cgm_report`
    │                               │
    └─────────┬─────────────────────┘
              ▼
     CGMReportService.parse_and_store
     ① 下载 PDF → 临时文件
     ② pymupdf 抽纯文本
     ③ StructuredResponseAgent + CGMReportExtraction schema 抽字段
     ④ 写 cgm_report 表(parse_status = success)
     ⑤ 同步覆盖画像近期风险(再跑一次结构化 LLM)
```

**关键设计**:两条上传路径**最后汇到同一个 service**。失败兜底统一,数据格式一致,以后改 schema 改一处就行。

### 表设计:为什么这样

`cgm_report` 表 [models/cgm_report.py](../../src/backend/AnTang/database/models/cgm_report.py) 的核心思路:

- **append-only,不去重**:每份报告独立一行,同一用户多份按 `monitoring_end_date` 取最新。报告是**时间窗口快照**,不能覆盖,否则失去趋势对比能力。
- **patient 数据匿名化**:不存姓名 / 手机号,只存病史标签 / 年龄 / 性别 —— 这是合规要求,而且关联 `user_id` 已经够用。
- **目标范围必存**:妊娠糖尿病 3.5-7.8 + TIR ≥90%,常规 3.9-7.8 + TIR ≥70%。这个字段以报告**自己声明的为准**,因为厂家会按用户病史自动选。
- **明细 JSON 字段两个**:`daily_metrics`(每天指标)+ `hourly_metrics`(分时段指标,只长报告才有)
- **`raw_text` 保留 PDF 抽出的纯文本**:方便重抽,失败时也能在 DB 里看到原文

### Tool / Skill 怎么分工

- `import_cgm_report` Tool:用户对话上传时触发解析入库
- `get_latest_cgm_report` Tool:用户问"我最近报告怎么样"时取数据
- `cgm_interpretation_skill` Skill:拿到数据后按 SKILL.md 模板生成对话式解读

主 Agent 会自动按 system prompt 里的指引串起来用:**先 get_latest_cgm_report 拿数据,再把数据塞进 query 调 cgm_interpretation_skill 生成解读**。

### Skill 里规定输出格式

[`skills/cgm_interpretation/SKILL.md`](../../src/backend/AnTang/skills/cgm_interpretation/SKILL.md) 严格规定了解读的 4 段结构(总体怎么样 / 关键数值看点 / 值得关注的细节 / 我的建议)、各段写法、危急信号触发的安全话术、按日点名的硬阈值规则。这就是 Skill 的真正价值 —— **把"医疗陪伴的输出规范"硬约束进 prompt**,不靠主 Agent 自由发挥。

### 一个踩过的坑:折线图里的数据 LLM 抽不出来

CGM 报告里有大量折线图(每日血糖曲线、AGP 图谱、多日对比曲线),它们都是**像素图**,pymupdf 抽出来只有文字层,折线点位丢失。

但是:**报告右侧 / 下方的明细表格是文字层**,LLM 能完整抽出来(daily_metrics 和 hourly_metrics)。所以视觉上看像是"折线图里的信息没了",实际上数值都在结构化字段里。

短期不打算用视觉模型读折线图,理由:文字明细表已经覆盖了主要解读需求,视觉模型读数值会引入幻觉(精度差 ±1-2 mmol/L,医疗场景敏感),每页加 3-5 秒延迟。如果以后真要做,优先做 AGP 图谱视觉理解(只一张图、概括性强、长报告才有),而不是逐日折线图。

## 八、其它值得知道的事

### `light_analyzer` 是怎么"理解"用户的

[`services/antang/light_analyzer.py`](../../src/backend/AnTang/services/antang/light_analyzer.py) 给小模型的 prompt 是结构化的:把短期历史摘要、当前用户输入、上轮的 dialog_state、血糖数值、文件 URL 这些塞进去,要求它输出一个 4 字段的 JSON(`understanding` / `core_worry` / `reply_rhythm` / `avoid`)。

它给主对话**注入的不是答案,是"看清问题的视角"**。

### `dialog_state` 是什么

每轮对话结束后,`_update_dialog_state` 根据 light_analyzer 和回复内容,提炼出一个 `DialogState`(当前阶段 / 主导情绪 / 上轮抛的追问)存进 history 表的 events 字段。下一轮开始时再从历史里读回来,塞给 light_analyzer 作为上下文。

这相当于**手动维护的对话状态机**,跟主 LLM 的对话历史是两套并行的东西。

### 知识库怎么工作

`data/antang_knowledge_pdfs/` 下放医学知识 PDF,后端启动时 [`services/antang/knowledge.py`](../../src/backend/AnTang/services/antang/knowledge.py) 异步把它们切片向量化进 Chroma(走 `pymupdf4llm` 转 markdown,再切 chunk)。主 Agent 有个 `retrieve_diabetes_knowledge` 工具,模型决定要不要调,调了就向量检索 + rerank。

PDF 同步是**启动时后台 task**,不阻塞健康检查 —— 这是个细节,因为知识库 PDF 可能很大,首次同步几分钟,等它完了再启动服务会让 docker healthcheck 超时。

### 部署

```bash
# 用 Docker:把 docker_config.example.yaml 复制成 docker_config.yaml,改 5 个 API key
docker compose -f docker/docker-compose.yml up --build -d

# 起来后:
# 前端 http://localhost:8090
# 后端 http://localhost:7860
# Swagger http://localhost:7860/docs
```

所有服务(MySQL / Redis / MinIO / 后端 / 前端)都在 docker-compose 里。第一次启动会跑数据库初始化、seed 系统 MCP、seed 系统 Skill、绑安糖心语 Agent、异步同步知识库 PDF。

### 配置三件套

| 文件 | 用途 |
|---|---|
| `docker/docker_config.example.yaml` | 配置模板,**仓库里维护它**,里面带详细注释 |
| `docker/docker_config.yaml` | 真实配置(包含 API key),**.gitignore 屏蔽,不上传** |
| `src/backend/AnTang/config.yaml` | 容器内的实际配置(Dockerfile 里把 docker_config.yaml COPY 过去覆盖) |

### `_ensure_antang_agent` 的执行时机

每次后端启动时跑,做的事:对比代码里的 `DEFAULT_ANTANG_SYSTEM_PROMPT` 跟数据库里"安糖心语"那条记录的 system_prompt,有差异就 UPDATE。**所以改 prompt 必须改源码 + 重启,直接改 DB 会被下次启动覆盖回去**。这是个有用的不变量,但也是个坑。

## 九、还可以怎么扩

这个项目结构稳定了之后,加新能力非常便宜。几个例子:

- **加新的内置工具** → 改 [`antang_agent.py`](../../src/backend/AnTang/core/agents/antang_agent.py) 的 `_build_antang_tools`,追加一个 `@tool` 闭包就行
- **加新的专项 Skill** → 在 `skills/` 下建个目录,写 SKILL.md,重启就生效
- **接新的 MCP Server** → 在 `config/mcp_server.json` 加一条,密钥填 `mcp_credentials`
- **接更多体检报告类型** → 复用 CGM 那套模式:抽字段 schema + service + 上传 + 内置 tool + 解读 Skill
- **画像加新维度** → 改 `AnTangUserProfile` 加字段,改 `PROFILE_UPDATE_PROMPT` 让 LLM 知道这个字段什么时候写
