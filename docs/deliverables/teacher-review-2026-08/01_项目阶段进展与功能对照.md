# 安糖心语项目阶段进展与功能对照

版本：V1.0（待补真机截图）  
日期：2026 年 8 月 10 日  
整理人：张旭睿  
审阅对象：赵增华老师

## 1. 阶段结论

安糖心语目前已经形成一个可以在 Android 真机运行的文字健康陪伴 Demo。已跑通的核心能力包括账号与连续聊天、DeepSeek 流式回答、联网搜索与来源、健康档案、Amazfit Active 2/Zepp/Health Connect 历史数据、Hindsight 长期记忆，以及主动关怀和系统推送的基础设施。

当前系统还不是完整医疗产品。血糖设备尚未接入，图片和报告只能在手机端选择预览，语音转文字、FoH 专业评估、健康异常正式关怀和普通聊天医疗审核仍未完成。现阶段最准确的表述是：

> 已完成可运行、可展示的患者端核心链路，并为长期记忆和主动关怀建立了真实基础设施；血糖、多模态、专业 FoH 和医疗安全闭环仍是下一阶段工作。

## 2. 对照方法

老师提供的《安糖心语 GlucoMind 软件需求规格说明书 SRS V1.2》描述的是包含患者端、监护端、研究端和管理端的完整平台。当前项目优先实现患者本人使用的 Android 首版，因此本文不把平台化目录数量当作完成度，而按实际用户功能进行对照。

状态含义如下：

- **已完成并验证**：代码已接通，并有自动化、真实服务或 Android 真机证据。
- **已实现待完整验收**：主代码完成，但还缺一个或多个真机场景或真实业务闭环。
- **部分实现**：只完成该需求的一部分，界面入口不等于后端能力完成。
- **未实现**：当前没有可用功能，不能用于演示成果。
- **当前版本不采用**：与当前患者端首版的产品边界不同，若后续确有需求再单独立项。

## 3. 当前 Demo 已完成的主要能力

### 3.1 账号与连续聊天

支持用户名注册、登录、登录状态恢复和退出。登录后进入唯一的连续聊天窗口，用户可看到 DeepSeek 流式回复、联网活动、历史消息、停止和失败重试。消息、Agent 运行和工具调用均保存在 PostgreSQL 中。

验证：Android 真机已运行；后端认证和聊天链路有自动化测试。

> [待插入截图 02：连续聊天主页]

### 3.2 联网搜索与来源

Core Agent 可以按问题需要调用 Tavily 搜索并读取网页，回答中展示可打开的引用和来源卡片。系统保存模型实际看到的规范化工具结果和来源，便于复核。

边界：功能已接通，但搜索覆盖率和医学答案正确性仍需持续评测，不能宣传为经过临床验证。

### 3.3 健康档案与确认卡

用户可以查看、填写、修改和撤回基础信息与健康情况。对话中识别到个人健康信息时，健康档案 Sub-agent 只提出候选，普通程序负责单位换算、范围校验、并发检查和写入。

“身高 169”会让用户确认厘米解释；“体重 100”不会擅自猜单位，而是提供公斤、斤和其他输入。用户不需要回到聊天重新描述。

验证：后端和移动端自动化已覆盖手动修改、网络重试、版本冲突、固定选项和自定义输入；真机逐项体验仍需在截图时完成复核。

### 3.4 手环历史数据

已经打通：

`Amazfit Active 2 → Zepp App → Health Connect → Android App → FastAPI → PostgreSQL`

真机已经读取并同步步数、锻炼、距离、爬升高度、体重、呼吸频率、静息心率、分钟级心率、睡眠阶段和血氧等十类 Zepp 数据。健康档案页面以只读方式展示最近观测时间，Core 也可以按用户问题查询服务器历史记录。

边界：这是最新可用的历史数据，不是服务器直接连接手环的实时监测；手环没电时不会继续产生新记录。

> [待插入截图 06：真实手环历史数据]

### 3.5 长期记忆

Hindsight 已以独立 Docker 服务上线。系统每累计三次成功 Core 对话，将尚未同步的完整消息段写入当前用户的记忆库；后续聊天和主动关怀只召回与当前任务相关的少量记忆。

真实语义回归已经覆盖短回复“对”的上下文、纠正与否定、助手猜测、重复写入、多用户隔离、主动关怀召回，以及 Hindsight API/数据库重启后的召回。

边界：长期使用中的记忆增长、Observation 后台整理和召回质量还要持续观察；当前没有用户逐条查看和管理记忆的页面。

### 3.6 主动关怀与系统推送

日常问候和用户明确同意的计划回访已经具备持久任务、独立 Worker、主动关怀 Agent、Auditor、Hindsight 上下文、免打扰、去重、聊天落库和 Expo Push 代码。

Firebase Android、EAS FCM v1、App Token 登记和后台系统通知已在真机跑通。第一次真实日常问候任务中，Agent 根据上下文合理选择跳过，因此没有伪造消息。

边界：还需完成一次“Agent 起草 → Auditor 通过 → 聊天落库 → 系统通知 → 点击定位”的真实完整验收。当前心率健康事件只做影子评测，不会向用户发送异常提醒。

## 5. 当前架构与原方案的主要差异

原 V3-E 方案设计的是 Kotlin/Spring Boot 业务内核、独立 Python Agent/算法服务、RabbitMQ、Redis、对象存储、七组件数字孪生和固定七类 Agent。当前项目为了先形成真实可运行的患者端产品，采用了更小的实现：

| 对比项 | 原 V3-E 目标方案 | 当前真实实现 |
| --- | --- | --- |
| 客户端 | Android 患者端及研究管理端 | Android 患者端 |
| 业务后端 | Kotlin/Spring Boot 模块化单体 | Python/FastAPI 单体 API |
| Agent | 独立服务中的固定七类 Agent | Core、健康档案、主动关怀、Auditor 四个角色 |
| 状态建模 | 七组件患者数字孪生 | 健康档案、设备观测、陪伴记忆分开管理 |
| 异步基础设施 | RabbitMQ、多个 Worker | PostgreSQL 持久任务和一个主动关怀 Worker |
| 文件基础设施 | S3/MinIO 对象存储 | 尚未接入，附件只到本地预览 |
| 长期记忆 | 自定义候选和确认体系 | 官方 Hindsight 独立服务及专用数据库 |
| 推送 | 统一推送/短信适配器 | Expo Push + Firebase FCM，Android 已通 |

这一阶段性裁剪降低了部署和调试成本，使聊天、手环、档案、记忆和推送能够在同一 Android Demo 中真实运行。相应代价是研究端、监护关系、对象存储和完整数据权利能力需要后续另行实现。

## 6. 测试与验收证据

截至 2026 年 8 月 10 日，本次重新检查结果为：

- 后端：270 项自动化测试全部通过，测试使用迁移到最新版本的临时 PostgreSQL 数据库。
- 移动端：23 个 Jest 测试套件、146 项测试全部通过；TypeScript 类型检查和 ESLint 通过。
- Android 真机：认证与聊天、Zepp/Health Connect 手动及前台同步、真实手环历史数据、Hindsight 服务冒烟、Expo Token 登记和后台系统通知已验证。
- 真实外部服务：DeepSeek、Tavily、Hindsight、Expo 和 Firebase 已在开发环境中调用。

这些证据证明工程链路能够运行，但不代表医学建议、FoH 干预效果、血糖预测或临床安全已经得到验证。

## 7. 当前未完成内容

### 高优先级

1. 接入真实 CGM/血糖设备，建立血糖同步、质量和时间语义。
2. 完成图片/文件上传、报告解析、CGM 报告长期保存和失败重试。
3. 为 Core 医疗回复增加发送前安全审核和无法安全回答时的阻断机制。
4. 完成一次真实主动关怀消息的全链路真机验收。

### 专项研究后再进入开发

1. 心率和血糖异常关怀的临床触发阈值、误报和急救边界。
2. FoH 量表、双风险分层和个性化干预。
3. 用户可查看和修正的记忆管理体验。
4. 研究任务、监护关系、数据导出删除和正式发布合规。
