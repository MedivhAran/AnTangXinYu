# 健康档案管理：当前设计

> 更新日期：2026-08-09  
> 当前状态：健康档案 Agent、页面手动维护、对话确认卡、Health Connect 同步均已接入。本文只记录仍然有效的设计和边界。

## 当前包含什么

健康档案分成三块：

- 基础信息：性别、年龄、身高、体重、常驻地区、作息和职业；
- 健康情况：病史、过敏、严重低血糖史和治疗情况；
- 手环数据：Zepp 经 Health Connect 同步的步数、锻炼、距离、爬升、体重、呼吸频率、静息心率、分钟级心率、睡眠和血氧。

前两块是用户能够查看和维护的长期档案。手环数据是带采集时间和来源的历史观测，只能由设备同步，不能在档案页面手工改写，也不能被一次异常读数自动变成疾病判断。

Hindsight 保存的是对话中的经历、偏好和关系线索，不属于健康档案，也不参与权威档案写入。

## 有依据的架构选择

LangChain 官方把 Sub-agent 描述为由主 Agent 委派、拥有独立上下文和工具权限的专业执行者；LangGraph checkpointer 保存一次运行的图状态，而不是业务档案。这支持当前分工：Core Agent 负责聊天，健康档案 Agent 只从当前表达中提出结构化候选，PostgreSQL 保存最终档案和审计历史。

Health Connect 官方同步方案要求按数据类型维护 Changes Token，并依据记录 ID、修改时间和删除事件同步变化。因此设备去重、删除、单位和时间校验由普通程序完成，不交给模型。

## 项目自己的实现决定

### 对话里识别档案变化

Core 只在当前消息确实涉及新增、修改、撤回或补充档案时，调用 `delegate_health_profile`。每次委派都会创建独立的子 AgentRun；健康档案 Agent 能看到当前档案、尚未处理的卡片、当前消息和最近五个完整对话轮次，但不能访问数据库写权限。

模型只负责理解自然语言并提出候选。普通程序再次检查原文证据、字段、单位、数值范围、用户归属和版本，然后决定直接写入还是生成卡片。子 Agent 的内部文字和工具结果不发给手机，Core 只拿到简短处理结果并继续回复用户。

明确且完整的信息可以直接写入；表达不确定时生成确认卡；缺单位、数值或必要内容时生成补充卡。裸数字的少数安全规则由程序处理：身高 `100–250` 建议理解为厘米，`1–2.5` 建议理解为米；年龄建议理解为岁。这些规则只生成确认卡，用户确认前不会写入。体重裸数字不猜单位。

### 卡片直接回答

卡片现在可以在聊天页原地处理，不需要用户再组织一句聊天消息：

- 身高 `169` 显示“是，确认写入”“不是这个”和“暂不写入”；点“不是这个”后可输入例如 `1.68 米`；
- 体重 `100` 显示“100 公斤”“100 斤”“其他”和“暂不写入”；
- 文本信息缺失时直接显示输入框；
- 健康情况缺少细节时显示与档案页相同的简单表单。

问题、固定选项和单位换算都由普通代码生成。回答卡片不会重新调用 Agent，也不会伪造一条隐藏聊天消息。服务器会重新检查卡片是否仍待处理、选项是否合法以及目标档案版本是否变化；网络重试复用同一操作编号。

### 档案页面手动维护

用户可以在健康档案页面逐项填写、编辑或清除基础信息，也可以新增、编辑或删除健康情况。编辑已有健康情况时类别固定；需要换类别时先删除再新增。页面不要求填写隐藏的起止日期，手动编辑会清除旧日期，避免保留用户没有重新确认的信息。删除健康情况在数据库中记为用户撤回，历史审计仍然保留。

页面操作和 Agent 候选共用同一套校验、单位换算和写库代码。手机为每次操作生成唯一编号并携带当前版本：相同请求重放不会重复修改；档案已经变化时服务器返回 `health_profile_changed`，手机刷新最新内容并要求用户再次确认。审计记录明确区分“来自 Agent”和“来自用户页面”。用户手动改动某个基础字段或已有健康事实后，只让指向同一目标的旧卡片失效，不影响其他待处理卡片。

健康档案 Agent 开始理解消息时会同时记住它所看到的各项目标版本。如果模型运行期间用户已经从页面改了同一项，旧的 Agent 结果会被拒绝，不能盖掉用户刚保存的内容；不相关项目的修改不会互相阻塞。

### 手环数据

Android 限定读取 Google Play 版 Zepp 写入 Health Connect 的十类记录。首次同步读取最近 30 天并建立每类独立 token，后续消费变化；服务器完整接收一页后才推进 token。记录 ID、修改时间、来源 App、记录方式和可用设备信息一起保存，删除事件形成墓碑。

前台手动同步和回到前台同步已通过真机验证；十五分钟 Android 后台周期同步代码也已接通，但仍需要 development build 真机验证系统调度。Changes Token 失效会明确停止该类型同步，目前不会用可能漏掉删除记录的方式静默重建。

Core 和健康档案 Agent 只能通过服务器注入当前用户身份的只读工具查询这些观测。回答必须保留观测时间，并说明这是服务器历史记录，不是此刻从手环实时读到的数值。

## 典型运行

用户说“我身高 169”时，健康档案 Agent 提出缺单位候选；程序把它转换成厘米确认卡。用户点“是，确认写入”后，服务器才保存 `169 cm`。用户也可以点“不是这个”并在卡片中改成 `1.68 米`。

用户说“我体重 100”时，程序保留数值但不猜单位。用户在卡片中点“100 斤”后，服务器换算并保存为 `50 kg`。这次回答不再经过模型。

用户也可以完全绕过聊天，从档案页面编辑自己的体重。该操作不会伪造聊天消息或 AgentRun，但会留下来源为用户页面的审计记录。

## 仍未解决

- FoH 状态、认知模式和干预档案的专业内容；
- 从设备或 CGM 数据形成长期规律的统计定义；
- Changes Token 失效后的无损完整历史重建；
- 用户批量导出、批量删除健康数据的产品流程；
- Core 医疗回答的实时安全审核。

这些内容需要单独确认需求和证据，不能从现有字段顺手扩展。
