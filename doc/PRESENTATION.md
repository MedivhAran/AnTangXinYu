## PR01
该产品的理想形态是面向医生与患者双方的糖尿病医疗服务平台，一端连接医院与医生，一端连接患者的日常生活。

- TOB端（医生端）：为医生提供患者血糖数据、病历信息、用药数据的可视化与管理平台。医生可以看到患者的连续血糖记录与趋势、用药方案和历史病历，结合患者日常的饮食、运动和睡眠情况，更准确地判断病情、调整方案，并与患者保持长期随访。
- TOC端（患者端）：为患者提供可穿戴智能设备（运动手表/手环）与授权品牌血糖检测仪（雅培瞬感、硅基动感）数据的可视化与分析平台。设备数据自动同步、长期保存，患者可以随时查看自己的血糖、运动、睡眠和心率趋势。
- 在数据之上，患者端接入长期陪伴的 Agent：它记住用户的健康档案和生活习惯，理解每一次对话的上下文，把设备数据和生活场景结合起来——解释血糖波动、回应日常饮食和运动问题、在低谷情绪时提供陪伴，并主动在合适的时间给予关怀，让健康数据真正融入生活，而不只是一张看板。

PR01 的核心是"数据 + 陪伴"：TOB 端让数据为医生服务，TOC 端让数据与 Agent 一起回到患者的日常。


## PR02 Agent 基座能力
Agent 基座是聊天体验的底层能力，目前已跑通并在 Android 真机上使用。

### 多轮交互
- 每个用户有一个持续存在的聊天窗口，历史消息全部在同一个窗口中延续，App 启动直接进聊天页。
- 对话越长，上下文越贵。系统在模型输入达到 15 万 token 时自动压缩：把较早对话提炼成摘要快照，保留最近 20 条原始消息，用户完全无感。
- 原始消息、摘要快照、每次运行的 token 用量全部落库，可审计、可回放。

### 主动追问
- 用户聊天中透露的健康信息（如"我最近血糖很高"），由健康档案管理 Agent 识别。
- 信息不完整时主动追问：缺少单位、数值或必要细节，会生成"补充信息卡"；表达不确定时生成"确认卡"。
- 卡片是 App 里的固定选项（选择单位、纠正、填写），用户直接点选即可，不用像客服一样来回打字。

### 多模态（图片理解、语音理解、用户体检报告解析）
- 已实现：拍照、相册图片和 PDF 报告上传，交给同一个多模态 Agent 解读（如 CGM 报告解析、体检报告阅读）。
- 报告中提取的明确健康事实和统计规律会进入健康档案，并保留来源报告和分析时间范围。
- 语音理解：规划中，尚未实现。

### 用户语义纠偏
- 用户纠正信息时（如"我上个月说的是晚餐前，不是空腹"），健康档案管理 Agent 会识别并更新，不靠关键词匹配。
- 纠偏行为在陪伴记忆中也有专门回归验证（纠正、否定、助手猜测等场景）。
- 健康档案页面支持逐项手动维护，页面操作和 Agent 候选共用同一套校验、冲突和审计逻辑。

### 主动关怀
- 独立的主动关怀 Agent，由健康事件、日常问候或计划回访直接触发，不走聊天对话。
- 触发门槛由程序把关：免打扰时段、最近刚聊过天、近 24 小时已主动发过消息都不会重复打扰。
- 关怀消息先由独立 Auditor 审核（只能通过或拒绝），再通过 Expo Push 推送，与连续聊天共用同一个窗口。

## PR03 高质量糖尿病医学知识库

- 资料来源：14 份糖尿病领域权威指南与专家共识 PDF，包括《中国糖尿病防治指南（2024版）》《中国 1 型糖尿病诊治指南（2021版）》、ADA/EASD 成人 1 型糖尿病管理共识报告、《持续葡萄糖监测基层临床应用专家共识》、动态葡萄糖图谱（AGP）临床应用共识、1 型糖尿病运动管理共识声明等，覆盖诊治、CGM、运动、胰岛素泵、低血糖管理和自我管理教育。
- 入库流水线：PDF 用 MinerU 解析成结构化 Markdown（大文件自动分片，避开显存瓶颈），清洗后按段落切片。
- 每个切片同时建三套索引：
  - Milvus 向量库：按语义相似度召回，"血糖高了怎么办"能命中表达不同但意思相近的段落；
  - Elasticsearch 关键词索引（BM25）：保证"糖化血红蛋白""黎明现象"这类专业名词精确命中；
  - LightRAG 知识图谱：自动抽取实体和关系，能回答需要跨文档关联的问题（如"指南 A 和共识 B 对运动后补糖的说法有何异同"）。
- 检索流程：先把用户问题改写成多个查询，双路召回后用 RRF 按名次融合（向量分数和关键词分数量纲不同，不能直接比大小），再用 rerank 模型精排，最后把最相关段落交给 Agent 组织回答。
- Agent 侧是普通工具调用：糖尿病知识库检索和图谱知识检索两个工具，按需使用、结果可审计。
- 维护是增量的：文件按 sha256 校验，新增、修改、删除自动同步，不用整库重建；配有 RAGAS 全链路评测脚本。

## PR04 可穿戴设备数据接入
- 首个接入设备是 Amazfit Active 2 手表。真机已验证：Zepp 会向 Android Health Connect 写入步数、锻炼、距离、爬升高度、体重、呼吸频率、静息心率、分钟级心率、带阶段的睡眠和血氧饱和度共十类数据。
- App 通过 Expo 的原生模块读取 Health Connect：权限申请、原生调用、手动同步和回到前台自动同步已通过真机验收；十五分钟 Android 后台周期同步代码已接通。
- 数据同步到服务器后由程序完成去重、单位和时间校验、统计计算，原始记录长期保存。Agent 通过"仅限当前用户"的只读工具查询，结果始终标注观测时间，不会当成实时测量来表述。
- 血糖检测仪（雅培瞬感、硅基动感）的数据接入在路线图中，尚未实现，属于后续阶段的血糖数据源。

## PR05 用户画像建模
用户画像是 Agent"懂这个人"的基础，分长期记忆和健康档案两条独立的线。

### 长期记忆
- 采用官方 Hindsight（v0.8.4）陪伴记忆系统，独立容器部署，配 PGroonga + pgvector 的 PostgreSQL，不与主数据库混用。
- 每累计三次成功对话，就按游标把新消息同步进记忆；Core 和主动关怀都会在线召回相关记忆。
- 语义回归已验证：短回复、纠正/否定、助手猜测、幂等、多用户隔离、主动召回等场景均通过；数据库重启后记忆不丢。

### 健康档案
- 健康档案是权威记录，用 PostgreSQL 持久化，与"记忆"分开：记忆是陪伴用的印象，档案是能审计的事实。
- 档案分三类：基础个人档案、健康与低血糖档案、**FoH（低血糖恐惧）状态与应对模式**。
- 写入流程有把关：健康档案管理 Agent 只提结构化候选，由程序校验、授权、写入并留审计记录；设备原始观测永远只读，模型推论不能直接写成档案。
- 有数据依据的血糖规律可以自动更新，并保留数据来源和统计时间范围；用户随时可以查看、纠正和删除。
- 手环观测、CGM 提取的事实、对话中识别的事实，最终都汇入这一份档案。

## PR06 血糖预测模型
- 规划中的能力，尚未实现。目标是基于 CGM 连续血糖时序数据做趋势预测与低血糖预警，为 Agent 的主动关怀和对话建议提供数据支撑。
- 当前处于调研阶段：血糖数据接入方案、预测触发规则和临床边界（心率阈值、误报、症状询问和急救边界）都需要先完成临床复核，再做模型选型和评测。
